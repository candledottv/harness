# Changelog

What changed in each version of Candle Harness (called the Candle TUI before 0.3.0). Versions follow [semantic versioning](https://semver.org), and each release is listed on [GitHub](https://github.com/candledottv/harness/releases).

## 0.6.13 (unreleased)

A published agent's Hyperliquid perps summary for a window (BE-3775), as Candle's CLI, local MCP server and SDK now read it: P&L and its parts, volume and fees to volume, rounds, win rate, largest win and loss, leverage, liquidations and max drawdown in dollars. Source is candle-monorepo `bdf8548b9`, #4073's merge on staging: CLI 0.13.39, MCP 0.10.42 and SDK 0.6.32, which wait on a promote and are not on npm yet. The shared source fixtures are re-read at that commit.

### The perps summary

- **A new read on three surfaces:** `candle agent <profile-id|slug> --perps [--window all|24h|7d|30d] [--json]`, `candle_get_agent_perps_summary` (the local server only; the hosted server's public list doesn't have it at this commit) and the SDK's `getAgentPerpsSummary(profileId, { window })`. Each reads `GET /api/v1/agent/records/:profileId/perps` once and sends no key, though one is configured. The tool and the SDK send a window only when one is given; the CLI always names it, `all` by default, and resolves a slug through the public slug read first.
- **Eighty-one offline rows** (`scripts/read-perps-summary-source.ts`, `test/fixtures/candle-perps-summary-source.json`) follow one made-up wallet through forty-one made-up days: five closed rounds, one in each window's own span and two in the last day, one position open at the build, and one builder-dex buy. Each answer is built by Candle's own pure source (the profile bundle and hourly components, the board figures, the publish over a prior build with two daily points, `perpsSummaryOf`), then read through the registered tool, the SDK, `candle agent <id> --perps` and `--json`. They give the same answer each time; the fixture keeps it once and each surface's row names it by hash.
- **Every figure checked by hand, in all four windows:** net = realized + funding - fees + unrealized; volume is px x sz over both legs of every fill, builder-dex fills included, with `builderDexVolumeUsd` their part; fees to volume is fees over main-exchange volume, since a builder dex's fee is charged in its own token and isn't in the record's fees; win rate is wins over decided rounds; largest win and loss are the best round above zero and the worst below; highest and average leverage come from the last Candle leverage action, else the highest a certified hour saw, and a round with neither is left out of both and counted in `leverageNotRecordedRounds`; liquidations count rounds the exchange closed. Drawdown is peak to trough of the cumulative perps P&L series the source reads (hourly inside 30 days; for `all`, the daily points before them from the first one), and each window's row carries that series where it moves.
- **Unknown is never zero.** A fill stored without its price is left out of the volume, counted in `volumeUnpricedFills`, and makes the summary `partial`. A bundle published before #4073 answers volume, fees to volume, leverage, liquidations and drawdown `null` while the record's own figures stay. Past 2 hours without a newer certified hour the same figures are served `partial`; past 3 the answer is `{ available: false, asOfMs, partial: true }`, no figure at all. A public agent with no perps history answers `summary: null`.
- **What the CLI prints:** the window (`(partial)` after it when partial), `As of <time>`, `Recorded since <date>`, then a table of figure, value and formula; `No perps history (all time).` and `Perps delayed since <time>; no summary now.` for the two answers without figures.
- **Refusals relayed as they are:** an agent that isn't published is 404 `RECORD_NOT_FOUND`, and a deployment that doesn't serve the board from Postgres is 503 `perps_summary_unavailable`, not retryable. The tool gives the body as an error, the SDK throws with the status and code, and the CLI exits 1 with the message. A window the command or tool doesn't take, no `--perps`, and a word that is neither an id nor a slug are refused before anything is read; an unknown slug stops after the slug read.
- **The chart's All / Spot / Perps split,** run as the pure function it is over a stand-in spot chart: each point carries `spotPnlUsd` and `perpsPnlUsd`, which add up to `totalPnlUsd`, a day before perps were published is all spot, and a spot-only chart comes back untouched. No agent surface reads the chart at this commit (the recorder searches the CLI, local MCP, SDK and hosted server sources), so the split is the web's alone.
- **Candle's own shared route answer** (`packages/shared/src/agent-perps-summary.fixture.json`) reads the same on every surface, and the public page's section, the read with each formula, is recorded as text (its three copies agree).
- **What the Candle Harness does:** `candle_get_agent_perps_summary` is classified as a read, in live and in paper, and `agent` (the bare word, `candle agent <id> --perps`) is in the command table as Candle's MCP read, so `candle_cli` points the agent at the tool. The answer is passed through unchanged; delayed perps and no perps history are answers, not errors.
- **As the source is at `bdf8548b9`,** recorded as it is: on a bundle published before #4073 the CLI prints an unknown leverage as `not recorded`, the words for a round with no recorded leverage, though the answer's `null` there means unknown; the volume line says `1 fills without a price left out`; and the summary tool is not on the hosted server.

### Returning a linked Solana submit at broadcast

Candle (BE-3929) now lets a linked Solana token trade's `POST /api/v1/trade/agent/submit` take `wait: "sent"` (`candle swap --wait-sent` in the CLI, `submit()` and `trade()` with `waitForTrade()` in the SDK) and answer HTTP 202 (`status: "broadcast"`, `signature`, `clientTradeId`) once the RPC acknowledges the send, while Candle confirms and books the trade in the background or through its `trading-background-booking` worker. Source is candle-monorepo `b5b0a1f75` (pull request #4039, unmerged), where the CLI says 0.13.47, MCP 0.10.45 and the SDK 0.6.39: draft until the release carrying BE-3929 is published, then re-read at it.

- **Eighty-five offline scenarios** (`scripts/read-wait-sent-source.ts`, `test/fixtures/candle-wait-sent-source.json`) run Candle's own source against stand-ins. Every fetch is intercepted; nothing reaches a database or a network, nothing is signed with a real key, and no address, key, signature or figure is real.
- **Broadcast acknowledgement vs inline confirmation:** `wait: "sent"` answers HTTP 202 at `onSent`, before the first status read, and runs its confirm loop with `resend: false`; the default `wait: "confirmed"` still resends while waiting and answers only after confirmation and booking. With no acknowledgement (an RPC send refusal, a lost send reply or a mismatched RPC signature), no 202 goes out: the route answers `SWAP_FAILED` at `stage: "unconfirmed"` (`retryable: false`) and keeps the reserved signature until the worker has chain proof.
- **Pre-send wire check and reservation fence:** `solanaWireSignatureVerifies` rejects a borrowed signature pasted onto a stamped build's message (`SIGNATURE_MISMATCH`) before either `reserveBackgroundBooking` or `recordSolanaBeforeSend` writes anything. Under the row lock, `reserveBackgroundBooking` refuses unbound bytes (`UNRECOGNIZED_TRANSACTION`) and fences against competing `wait: "sent"` and `wait: "confirmed"` submits (`IDEMPOTENCY_CONFLICT` at `stage: "not_broadcast"`), so of two competing submits for one trade, only one sends. `projectedDoc` keeps `backgroundBooking` inside Postgres.
- **Background booking and worker recovery:** concurrent runs of `confirmSolanaTrade` as the API's background confirm (holding `submittedWire`) and the worker's recovery (holding only the recorded `signature`), in either order, book the trade once with its full stamped fee and fire key usage, `trade.executed` and referral accrual once each. A bound landed revert settles the row as `failed` with `TRADE_REVERTED` and its signature; an unbound background confirm answers 500 `SWAP_FAILED` (`retryable: true`) and books nothing. `trading-background-booking` (`runResolvePass` every 15 s) confirms marked rows, leaves an unseen transaction built with its signature and hold (`unseen`, falling to the ledger's finality proof only past 30 minutes), and re-checks `state = 'built'` so a trade the request booked first is never confirmed twice.
- **The SDK and the CLI:** `submit()` and `trade()` forward `wait: "sent"`, return `BroadcastTradeResult`, and refuse invalid `wait` values, `"main"` payers and Hood mints before any request; `waitForTrade()` polls `GET /api/v1/trade/agent/jobs/:id` until `confirmed` or `failed`. `candle swap --wait-sent` exits 0 at broadcast on a Solana TEE token trade, refuses `--wait`, base-to-base pairs, bridges, Hood pairs and embedded payers (`USAGE`, exit 2, nothing built), and `candle swap status <id>` follows the job.
- **Mapped codes only, and nothing in the Candle Harness asks for `wait: "sent"`:** every code in the recording (`IDEMPOTENCY_CONFLICT`, `SIGNATURE_MISMATCH`, `SWAP_FAILED`, `TRADE_REVERTED`, `UNRECOGNIZED_TRANSACTION`, `USAGE`, `VALIDATION_FAILED`) maps to `refused`, `failed` or `unknown`, and an exit-0 `status: "broadcast"` answer maps to `unknown` until the trade job confirms. `teeSwapArgs` never passes `--wait-sent`, `candle_cli` refuses `--wait-sent` against the pinned CLI table (`candle swap has no --wait-sent flag.`), and the signed CLI release pin (`install.sh`), the runtime minimum (0.13.28) and the shared source fixtures stay where they are until BE-3929's release is published.

## 0.6.12 (unreleased)

Source is candle-monorepo `ebd1e5005`, #3921's merge on staging, the same build 0.6.11 pins: the published CLI 0.13.35, MCP 0.10.40 and SDK 0.6.29. The recording was first made at #3921's open head `36d4bf264` and re-read at the merge; no record row changed, only the commit and the versions it names. The source/build version is 0.6.12; publishing remains a separate release step.

### The agent record, perps included

- **A new read on three surfaces:** `candle agent record <profile-id> [--cursor <cursor>] [--json]`, `candle_get_agent_record` (the local server, and one of the hosted server's thirteen public tools) and the SDK's `getAgentRecord(profileId, { cursor })`. Each asks the record route for `rows=all` in one read and sends no key, though one is configured.
- **Eighty-four offline scenarios** (`scripts/read-record-source.ts`, `test/fixtures/candle-record-source.json`) follow one made-up wallet through three made-up days. Each answer is built by Candle's own pure source (the perps profile, the board's publish, the record composition, the round rows, the merge of swaps and rounds and its cursor) from stored facts the recorder writes, over a stand-in spot record, then read through the registered MCP tool, the hosted server's route, the SDK, `candle agent record` and `candle agent record --json`. The five give the same answer each time; the fixture keeps each served answer once and the hash of what each surface gave.
- **Perp rounds among the swaps:** closed rounds and spot swaps are one list, newest first, each row marked `trade` or `perp_round`. A round is placed by when it closed, and at the same time as a swap the swap comes first. An agent with no swap lists its rounds alone; one with no perps lists its swaps alone. The rounds are still beside the record as `perpRounds` too.
- **The round row:** `size` (the largest reached), `entryPx` (the average at that size: 2 at 3000 and 1 more at 3060 is 3020), `exitPx`, `leverage` and where it came from, `initialMarginUsd` (entry average x largest size / leverage), `returnPct` (net P&L over that margin), `fundingUsd` (positive when earned), `feesUsd`, `durationMs`, `liquidated`, the closing fill's `hash` and the round's id. No wallet and no account value.
- **Leverage and where it came from:** the last Candle leverage action before the open (`leverageSource: "order"`), else the highest a certified hour saw during the round (`"snapshot"`). A round opened and closed between two certified hours with no leverage action has none: `leverage`, the margin and the return are null, the CLI prints `leverage not recorded` and `ROE unknown`, and its P&L still counts as a win or a loss.
- **A liquidated round** is marked `liquidated: true` (the CLI: `LIQUIDATED`), at the loss the exchange closed it at.
- **Unknown is never zero.** From facts stored before fill prices were kept, sizes and averages are null and so is the return, while the certified P&L, fees and funding are unchanged. A bundle published before the added fields has none of them on a round: the CLI prints `size unknown`, `entry unknown`, `exit unknown`, `ROE unknown`, `funding unknown`, `fees unknown` and `duration unknown`.
- **The P&L breakdown:** the record carries `perpsRealizedUsd`, `perpsFundingUsd`, `perpsFeesUsd`, `perpsUnrealizedUsd` and `perpsNetUsd`, and they add up (realized + funding - fees + unrealized). The headline is the spot record plus the perps net. The web's own split of that headline, run here as the pure function it is, adds up exactly: spot, perps realized, funding, fees as a cost, perps unrealized and creator fees; an agent with perps only has a spot part of exactly zero. With creator fees not valued, or one perps component absent, that part and spot are both missing rather than worked out by subtraction, and a known zero stays a zero.
- **The best closes come from the server:** `perpsTopCloses` beside the record holds the best rounds of all time by net P&L, and the best-closes answer puts the spot closes among them, five at most, by dollars then newer first. Each best round is a listed row with its closing fill.
- **How fresh, and why there are none:** `perpsAsOfMs` is the certified time of the perps figures and `perpsCoverageFromMs` the start of stored coverage. Past 2 hours without a newer certified hour the same figures are served with `perpsPartial`. Past 3 hours the perps are unavailable: the record says `perpsUnavailable` and still gives `perpsAsOfMs`, the last certified time, so an agent can say since when; it carries no perps figure, round or best close, the list is the swaps alone, and the headline is the spot record's, never a flat book. A wallet no hour has certified yet is unavailable with no perps time.
- **What the CLI prints:** the agent's name, then `Perps as of <ISO time>`, with ` (partial)` or ` (unavailable)` after it, or `Perps as of not recorded`; then one line a row. A swap is `buy MOON 120`. A round is `Long ETH 10x · size 3 · entry 3020 · exit 3150 · +$383.25 · 42.3% ROE · funding -1.2 · fees 5.55 · duration 7200s · <explorer link>`. A further page ends with `Next page: --cursor <cursor>`.
- **Paging:** a page ends where the stored chunk of swaps it read ends, and its `rowsCursor` (`u1:`, pinning both the swaps and the rounds) reads the rest. The two pages together are the one list, each counts the whole list in `rowsTotal`, and the second is asked for with `rows=all` and the cursor on every surface.
- **Refusals are relayed as they are:** an agent that is not published (private, hidden, revoked or unknown, one answer for all) is 404 `RECORD_NOT_FOUND`, and a cursor from a record that has changed is 400 `VALIDATION_FAILED`, "Record changed; restart paging". The MCP tools give the body as an error, the SDK throws with the status and code, and the CLI exits 1 with the message. A name that is not a profile id (`candle agent record momentum`) is usage, exit 2, and a cursor that is not text is refused by the tool's schema; neither reads anything.
- **What Candle's tools and docs say:** the local and the hosted tool descriptions and the public agent-trading page's three paragraphs (the read, the round row, the perps times; its three copies agree) are recorded as text.
- **What the Candle Harness does:** `candle_get_agent_record` is classified as a read, in live and in paper, and `agent record` is in the command table as Candle's MCP read, so `candle_cli` points the agent at the tool. The answer is passed through unchanged; unavailable perps are an answer, not an error.
- **Source fixtures at `ebd1e5005`:** the record fixture is recorded there (84 rows, 8 builds). The shared fixtures (the CLI table with 177 commands, tools/list with 109 tools, the MCP/SDK scenarios and the perps, spot, transfer, freshness and webhook rows) were already re-read at that commit by 0.6.11 and are taken as they are; `agent record` and `candle_get_agent_record` were added there for parity, so this entry adds no command row or classification of its own. The freshness contract also checks that an unavailable record carries the flags at its top level with the last certified time.
- **As the source is at `ebd1e5005`,** recorded as it is: the record's rounds and figures are the default dex's only, so a round on a builder dex is not counted in it, though a round row keeps a `dex:COIN` name whole and Candle's own shared route answer has one (both are recorded); the CLI's human view prints its perps line for every record, so an agent with no perps reads `Perps as of not recorded`; and the human view has no P&L line, the breakdown's figures being in `--json`, the MCP tools and the SDK.
- The recording holds no wallet address, key or account value: the made-up wallet's address goes into Candle's source, which hashes it, and is in no row; every token, figure and fill hash is made up. No database, perps job, venue, signature or network was used, the keyed API route isn't run, and no staging or production read was made.
- Not here: the agent page itself (the breakdown as drawn, the claims tab, the chart's first perps day), which is the web's; and any live read of a published agent's record. The signed CLI release pin (`install.sh`) and the runtime minimum (0.13.28) don't move.

### Where a holder stands if a launch does not migrate, and the exit

- **Ninety offline rows** (`scripts/read-holder-exit-source.ts`, `test/fixtures/candle-holder-exit-source.json`) read ten holder-exit states and six exit outcomes through `candle token exit <token>`, `candle_holder_exit`, `candle_claim_holder_exit` and the SDK's `getHolderExit()` and `holderExit()`. The read's body is Candle's own pure `deriveHolderExit` on made-up chain facts at one block; the agent route's answers are response stubs shaped by the SDK's types and the route's refusal table. Every request is intercepted; the route, the chain, the builder and the signer are not run, and every address and hash is made up.
- **The states:** none, awaiting migration (Recovery opens for the creator at day 7 and for anyone at day 30), Recovery open (`enter_recovery`), Recovery (a fixed rate by tokens held, a wallet's balance and what Recovery pays it, `claim_recovery`), a wallet with nothing to claim, a pending rescue request and a void one (`quote_readmitted`), rescued (no on-chain claim), and a team escrow that is claimable (`claim_team`) or stranded. The disclosure is the API's sentence: the CLI prints it verbatim, the MCP tool and the SDK relay it whole.
- **The exit:** a dry run signs nothing (`not_started`), and the MCP tool's `dryRun` defaults to true while the SDK sends false unless asked. A completed exit has both calls confirmed and the claim booked. A partial one (the approval landed, the claim reverted) and an indeterminate one (a call sent, its result not known: the CLI exits 3) are refusals carrying `outcome`, `calls` and `warnings`. `HOOD_RECOVERY_NOT_READY` keeps its two times in `details`, and a declined confirmation exits 5 with only the dry run sent. An exit has no keyless form: the MCP tool and the SDK refuse before any request.
- **Keyless reads:** the MCP tool and the SDK make one GET of the curve's route, with `?account=` when a wallet is named; the CLI reads the token's market for its curve first. Given a token, the MCP tool reads its market first, and a token with no Hood curve is `NO_HOOD_CURVE`.
- **`candle portfolio` marks** a Hood position in `recovery`, `rescue_pending` or `rescued` (`holderExits`, `holderExitsUnread` and `holderExit` on the holding in `--json`). The run needs a wallet read, prices and a chain, so it is pinned as the source's own text and not run here.
- **What the Candle Harness does:** `candle_holder_exit` is classified as a read. `candle_claim_holder_exit` moves funds from the account's wallet and has no card yet, so it is refused by name and not offered, pointing at the read; `candle token exit` through `candle_cli` is a read (with `--dry-run` too), and `--recover`, `--enter-recovery` and `--claim-team` are funds-out rows held for later. `--yes` is never the agent's.
- **Source fixtures re-read at `31e075fe6`:** the CLI table (176 commands; `token exit` new), tools/list (108 tools; `candle_holder_exit` and `candle_claim_holder_exit` new, `candle_get_market`'s description gains the holder-exit disclosure), and the 94 MCP/SDK scenarios, and the 25 perps, 59 spot, 67 freshness, 49 webhook and 39 perp market rows. An agent build on the same connection warms the web's buy; three buys at once share one hash read, while each reads the table (the table cache has no shared read). A buy whose table can't be read composes without it, and the next buy reads it again. A failed hash read builds nothing to sign.
- **A table that grew since it was cached:** the message overflows, the composer reads the tables again once and keeps the fee; when the route still doesn't fit, it falls back to Jupiter's own fee-free transaction exactly as before (`input_fee_packet_limit`).
- **Pinned as source text,** since the handlers sit behind auth, Convex and the database: the web buy uses the process's one connection and no priority cap; the trade build starts the route breaker's read and the linked payer's read together, still answers `SWAP_ROUTE_FAILING` before the payer is used, starts the feed read early, and reads wallets on the fresh path; DFlow's quote budget is 400 ms.
- **Mapped codes only:** the build's checks answer `SWAP_ROUTE_FAILING`, `AGENT_WALLET_MISSING` and `VALIDATION_FAILED`, each of which the Candle Harness reads as refused with nothing sent. Nothing in the Candle Harness changes, and the CLI release pin and the runtime minimum don't move.

### The client-surface header and the per-swap timing fields

Candle (BE-3919) now names the client on every request to its API, `X-Candle-Client: <surface>/<version>` (`cli`, `sdk`, `mcp`, `mcp-hosted`, `web`), and records, for each Solana swap its API broadcasts, the send time, the landing slot and the path that won. Each surface's own header, replayed into a route, lands as that surface's label. A send the RPC refused, a broadcast outside the swap routes and a process with no writer record nothing; what the trade sees is unchanged in every case.
- **The confirm loop** reports the slot and the send count once, when a confirmed status is read (not a processed one). The table's columns and checks are pinned as source text: no wallet, mint, amount or account.
- Nothing in the Candle Harness changes: it doesn't call the Candle API itself, so the CLI and MCP server it runs send the label. The CLI release pin and the runtime minimum don't move. Not here: the database write, the migration and the read query, which need Postgres.

Any other link is withheld: the pane names its host and says not to approve, and the step ends unapproved when its code expires. Other owner steps print the CLI's own words as they are.
- **Candle's trading-wallets read is read to its last page, and decides.** Where the agent's MCP server has it, every page is read (up to ten). A complete read is the whole list of what may trade, so a wallet it leaves out can't pay, whatever the key's own list says. A read cut short leaves the wallets it didn't reach as the key's list says.
- **A Solana wallet is never taken for a Hood one** when the key's list and the portfolio are matched by address.

### Tests

- The wallet join by address has tests that fail if it's reverted to ids: another id with no trading read, a Hood address in another letter case, and a Solana address in another case, which is another wallet.
- The trade-path bench is held to 50 ms again, and isn't part of the release gate: on a shared CI runner it measured the runner rather than the code.

### Hood TEE wallets trade

- **An agent trades from its Hood TEE wallet.** A Hood TEE wallet bound to an agent's key was listed and refused every trade with "trades from Hood TEE wallets come in a later release". Now a buy or sell of a Hood token, against ETH or USDG, and a swap between ETH and USDG, pays from it, through your own `candle swap` with the agent's key, as a Solana TEE wallet's trades do. The CLI signs it one leg at a time; the card binds the same words, and an unclear answer is read back under the same id, never sent twice.
- **Which wallet a Hood trade pays from.** Named, a Hood TEE wallet pays only for a Hood trade: named for a Solana token it's refused as the wrong chain, as a Solana wallet is for a Hood token. Naming no wallet, a Hood trade pays from the EVM embedded wallet where the key is allowed it, else from the key's one Hood TEE wallet, as `candle swap` picks. With more than one, name it or set `agents.<name>.wallet`. As a default, a Hood TEE wallet is kept by address, so a rename doesn't lose it.
- **Candle's RPC setting stays on Solana trades.** `candle.rpcUrl` is a Solana endpoint, so a Hood TEE card runs without `--rpc-url` and the CLI reads Hood over its own.
- **A busy Hood TEE wallet is refused, nothing sent.** A Hood TEE wallet runs one operation at a time: while another is open on Candle (`WALLET_BUSY`), or when Candle answers without a sequenced leg, the card is refused and says so.
- **Percent sells see a Hood wallet's holding.** The card's estimate reads the wallet under the portfolio's `hood`, its address and token in any case.
- **The doctor checks a Hood TEE wallet's signer**, as it does a Solana one's, instead of saying it comes later. The kill switch lists Hood TEE wallets with `candle tee disable <address>`, and autonomy and the agent's wallet note count them.

The first release since 0.3.0, and it carries everything in 0.5.2, 0.5.3 and 0.5.4 below. **Update from 0.3.0:** see the first line under 0.5.2's "Safety and correctness".

### Candle CLI 0.13.20

- **Owner steps wait for your approval in the browser.** Candle is turning on a browser confirm for owner steps that widen a key's reach: making a key, allowing the embedded wallet, rebinding or promoting a wallet to a key, raising a cap. An older CLI can't finish those steps once it's on. The Harness now needs CLI 0.13.20, and its installer installs it. The prompt pane shows what you're approving, the link and the code, and waits up to 5 minutes. A card for such a step says so before you start. Denied or expired, nothing changes, and the card says which, in plain words.

### Safety and correctness

- **`restart it` starts the login service's core only for the service's own home.** With the service installed for one Harness home and a view open on another (`CANDLE_HARNESS_HOME`), `restart it` stopped the view's core and started the service's, for the other home: the view's home was left with no core, and the other home's triggers and bots started. Now a view on another home restarts a core of its own.
- **On a Mac, the code runner stops only its own run's processes.** At the end of a run, it stops anything the script left behind in its sandbox, a double fork included. It used to take a process in any sandbox that started during the run, so another app's sandboxed helper could be stopped. Now each run's sandbox carries a mark of its own, and only processes macOS says are held by that mark are stopped.
- **A default of `embedded` pays on either chain.** Set as an agent's default, `embedded` was pinned to the Solana embedded address, so every Hood trade that named no wallet was refused. Now it pays from the embedded wallet on the trade's chain. On paper, the input line takes either embedded address too.
- **A click right after a Build card closes approves nothing.** After a Build card closes, by a click, ⏎ or ctrl-n, clicks on cards wait 300 ms, so the second half of a double click can't approve or reject the card beneath.
- **An edit to `bots.toml`, `triggers.toml` or `wallets.toml` right after the Harness wrote it is read.** Each file was read again only when its modified time, size or inode changed. Two writes of the same size within one tick of the clock (a few milliseconds) looked like one, so a quick edit by a script or an agent, such as a bot paused in its file just after it was approved, could go unseen. Now a file changed in the last two seconds is always read again.
- **A TEE wallet made by `vault promote --to-key` can trade.** Such a wallet signs and trades, but the key's wallet list says it can't (`spendCapable: false`) and gives it another id than the portfolio does. The Harness took the list at its word and refused every trade from it with "Candle doesn't list it as able to sign yet". Now, where your agent's Candle MCP server has `candle_get_trading_wallets` (CLI 0.13.19 and later), that read decides whether a wallet can trade, and the wallets are matched to the portfolio by address, not id. With an older CLI, the key's list decides as before.

### Triggers

The folder holds `AGENTS.md` with the rules every bot runs under, the client, and nine of Candle's bot-building skills; a file you change is never written over.
